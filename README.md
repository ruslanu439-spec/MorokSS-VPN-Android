# MorokSS

## Android

Android-клиент лежит в папке [`android`](android). Он запускает MorokSS как фоновую службу,
хранит импортированный профиль через Android Keystore и отдаёт локальный Shadowsocks-транспорт на
`127.0.0.1:8389`. Готовая инструкция есть в [`android/README.md`](android/README.md).

MorokSS — экспериментальный транспорт для Shadowsocks.

Он прячет исходное соединение внутри TLS и WebSocket. Снаружи сервер выглядит
как обычный HTTPS-сайт. Сам Shadowsocks при этом продолжает работать локально и
не принимает подключения из интернета.

Это ранний прототип. Он усложняет распознавание соединения, но не даёт гарантии
от блокировки IP, домена или хостинга.

## Вот как это работает

```text
приложение
    ↓
локальный клиент Shadowsocks
    ↓
клиент MorokSS
    ↓ TLS + WebSocket или HTTP stream, порт 443
сервер MorokSS
    ↓
Shadowsocks на 127.0.0.1
```

Клиент подключается по секретному пути. Путь меняется каждый день и считается
из общего ключа.

После подключения клиент отправляет HMAC-подпись, время и случайный `nonce`.
Старый пакет нельзя использовать второй раз. Небольшие сообщения дополняются
случайными байтами, чтобы их размеры не были постоянными.

Если сканер не знает секретный путь, MorokSS передаёт запрос обычному сайту на
локальном nginx. Сканер видит сайт, а не ответ от прокси.

## Что уже есть

- TLS, стандартные WebSocket-кадры и запасной HTTP stream;
- секретный путь с ежедневной ротацией;
- HMAC-проверка клиента;
- защита от повторной отправки пакета;
- ограниченное заполнение размеров сообщений;
- автоматический выбор рабочего TLS ClientHello;
- автоматический выбор транспорта;
- автоматическое переключение между несколькими адресами сервера;
- подписанный список endpoint с локальным кэшем;
- ротация общего секрета без остановки сервера;
- TCP и UDP до локального Shadowsocks;
- локальная диагностика TCP и UDP без автоматической отправки отчёта;
- сайт-приманка для посторонних запросов;
- пример systemd-сервиса;
- сквозной тест соединения;
- CI, fuzz-тесты и сборка релизов для основных систем.

Мультиплексирования нескольких TCP-подключений в одном туннеле пока нет.

## Установка

Для сервера нужен Python 3.11 или новее. Для рекомендуемого клиента нужен Go
1.24 или новее.

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install .
```

Для запуска тестов:

```bash
pip install -e ".[dev]"
python -m unittest discover -s tests -v
go test ./...
```

Полный тест между Go-клиентом и Python-сервером запускается отдельно:

```bash
MOROKSS_RUN_GO_TESTS=1 python -m unittest discover -s tests -p "test_go_client.py" -v
```

## Сервер

Сначала запусти Shadowsocks на `127.0.0.1:8388`. Не открывай этот порт наружу.

На `127.0.0.1:8080` должен работать простой сайт, например nginx. Он нужен для
ответов на обычные запросы.

```bash
export MOROKSS_SECRET="$(openssl rand -base64 48)"

morokss-server \
  --listen 0.0.0.0:443 \
  --backend 127.0.0.1:8388 \
  --decoy 127.0.0.1:8080 \
  --cert /etc/letsencrypt/live/example.com/fullchain.pem \
  --key /etc/letsencrypt/live/example.com/privkey.pem
```

Сохрани значение `MOROKSS_SECRET`. На клиенте нужен тот же ключ.

### Смена общего секрета

Сервер может временно принимать два секрета. Сначала установи новый ключ как
`MOROKSS_SECRET`, а старый оставь в `MOROKSS_PREVIOUS_SECRET`:

```bash
MOROKSS_SECRET="новый-секрет"
MOROKSS_PREVIOUS_SECRET="старый-секрет"
```

Потом обнови клиентов. Когда старых клиентов не останется, удали
`MOROKSS_PREVIOUS_SECRET`. Постоянно хранить старый ключ не нужно.

Примеры для systemd лежат в папке [`deploy`](deploy).

## Клиент на Go

Этот вариант рекомендуется для обычного использования. Он использует
[uTLS](https://github.com/refraction-networking/utls) и формирует ClientHello,
похожий на браузерный.

Сборка:

```bash
go build -o morokss-client ./cmd/morokss-client
```

Запуск:

```bash
export MOROKSS_SECRET="тот-же-секрет"

./morokss-client \
  --listen 127.0.0.1:8389 \
  --server example.com:443 \
  --hostname example.com
```

Если серверов несколько, добавь их через повторяющийся `--endpoint`:

```bash
./morokss-client \
  --listen 127.0.0.1:8389 \
  --endpoint 203.0.113.10:443,one.example.com \
  --endpoint 203.0.113.20:443,two.example.com
```

Слева от запятой идёт адрес подключения. Справа — имя из TLS-сертификата.
Старые `--server` и `--hostname` продолжают работать для одного адреса.

Клиент сначала пробует последний рабочий endpoint. Если адрес, маршрут или
сервер не отвечает, он переключается на следующий. Неудачный адрес получает
паузу от 30 секунд до 8 минут. Так клиент не стучится в него при каждом новом
подключении. Рабочий адрес хранится в локальном кэше. Путь меняется через
`--endpoint-cache`; пустое значение отключает кэш.

Для каждого endpoint хранится свой результат выбора TLS-профиля. Проверка
начинается только при настоящем подключении. Фоновых запросов нет.

По умолчанию также включён `--transport auto`. Сначала клиент пробует WebSocket.
Если сервер или промежуточное оборудование отклоняет Upgrade, клиент пробует
`http-stream`. Этот режим использует двусторонний HTTP/1.1 с chunked framing.
Рабочий транспорт запоминается отдельно для каждого endpoint.

Можно закрепить режим вручную:

```bash
./morokss-client \
  --endpoint example.com:443,example.com \
  --transport http-stream
```

Путь к кэшу меняется через `--transport-cache`. HTTP stream — это запасной путь,
а не обещание обхода любой фильтрации.

По умолчанию включён `--profile auto`. Клиент использует последний рабочий
профиль. Если соединение ломается во время TLS-handshake, он временно исключает
этот профиль и пробует следующий. Успешный вариант сохраняется в локальном кэше.
Проверка запускается только при настоящем подключении. Фонового сканирования нет,
чтобы не создавать постоянный поток пробных соединений.

Клиент различает этапы `tcp`, `tls`, `websocket`, `http-stream` и `auth`.
Например, ошибка сертификата или недоступный IP не запускают перебор ClientHello. Иначе клиент
создавал бы лишние подключения, хотя смена профиля ничего не исправит.

Доступны профили `chrome`, `firefox`, `safari`, `edge`, `ios`, `android` и
`randomized`. Конкретный профиль можно закрепить вручную через `--profile`.
Путь к кэшу меняется через `--profile-cache`; пустое значение отключает кэш.

## Подписанный список серверов

Список endpoint можно обновлять без выпуска новой настройки клиента. Сначала
один раз создай Ed25519-ключи:

```bash
go build -o morokss-manifest ./cmd/morokss-manifest

./morokss-manifest keygen \
  --private morokss-manifest-private.key \
  --public morokss-manifest-public.key
```

Закрытый ключ оставь только у администратора. Не клади его на сервер с публичным
сайтом и не добавляй в Git.

Теперь подпиши список. Документ живёт не больше 31 дня:

```bash
./morokss-manifest sign \
  --private morokss-manifest-private.key \
  --out endpoint-manifest.json \
  --valid-for 168h \
  --endpoint 203.0.113.10:443,one.example.com \
  --endpoint 203.0.113.20:443,two.example.com
```

Файл можно раздать через обычный HTTPS-сайт. Клиенту нужны URL и открытый ключ:

```bash
./morokss-client \
  --endpoint-manifest https://updates.example.com/endpoint-manifest.json \
  --manifest-public-key ./morokss-manifest-public.key
```

Клиент проверяет подпись, срок действия и формат каждого адреса. HTTP без TLS не
принимается. Если сайт обновлений временно недоступен, используется последняя
проверенная копия. Статические `--endpoint` можно оставить как запасной вариант.

После авторизации сервер подтверждает, что локальный Shadowsocks доступен. Только
после этого профиль считается рабочим. Со старыми версиями без подтверждения
клиент продолжает работать в режиме совместимости.

Теперь укажи `127.0.0.1:8389` как адрес удалённого сервера в локальном клиенте
Shadowsocks.

Флаг `--insecure` отключает проверку сертификата. Он нужен только для локальных
тестов.

### Android VpnService

Встроенный Android-клиент запускает MorokSS внутри `VpnService`. Чтобы внешнее
соединение не попало обратно в VPN и не зациклилось, клиент принимает путь
к Unix-сокету через `--protect-path`. Дескриптор каждого TCP-туннеля передаётся
сервису через `SCM_RIGHTS`, после чего сервис вызывает `VpnService.protect()`.

```bash
./morokss-client \
  --listen 127.0.0.1:8389 \
  --udp-listen 127.0.0.1:8389 \
  --protect-path /data/user/0/com.example.app/no_backup/protect_path \
  --endpoint 203.0.113.10:443,example.com
```

Флаг нужен только внутри Android VPN. Обычный desktop-запуск его не использует.

### UDP

Если локальный и серверный Shadowsocks поддерживают UDP, включи локальный UDP
listener на том же адресе:

```bash
./morokss-client \
  --listen 127.0.0.1:8389 \
  --udp-listen 127.0.0.1:8389 \
  --endpoint example.com:443,example.com
```

TCP и UDP могут слушать один порт одновременно. Для каждого локального UDP
клиента создаётся отдельная ассоциация. После двух минут без пакетов она
закрывается. Время меняется через `--udp-idle-timeout`.

UDP отдельно выбирает endpoint, TLS-профиль и транспорт. Поэтому неудачный UDP
сервер не отправит рабочий TCP endpoint в cooldown. На сервере датаграммы идут
на UDP-порт из `--backend`.

### Диагностика

Чтобы проверить соединение и не запускать локальные listener, используй
`--diagnose`:

```bash
MOROKSS_SECRET='твой-длинный-секрет' ./morokss-client \
  --diagnose \
  --diagnose-network all \
  --endpoint one.example.com:443,one.example.com \
  --endpoint two.example.com:443,two.example.com \
  > morokss-report.json
```

`tcp` проверяет только TCP, `udp` — только UDP, а `all` — оба режима. Клиент
дожидается ответа готовности от сервера и сразу закрывает туннель.

В отчёте есть номер проверенного endpoint, TLS-профиль, транспорт, этап сбоя и
время подключения. Общего секрета, полного текста ошибок, адресов и доменов там
нет. Такой файл можно прислать для разбора.

Флаг `--diagnose-include-endpoints` добавляет адреса и домены. Не включай его,
если собираешься публиковать отчёт.

Отчёт показывает место сбоя, но не называет его причиной. Например, ошибка на
этапе TLS может означать фильтрацию, проблему сертификата или обычный сетевой
сбой.

## Клиент на Python

Python-клиент оставлен как простой запасной вариант:

```bash
morokss-client-py \
  --listen 127.0.0.1:8389 \
  --server example.com:443 \
  --hostname example.com
```

Его TLS-отпечаток отличается от браузера, поэтому Go-клиент предпочтительнее.

## Ограничения

Один endpoint не поможет, если заблокирован его IP или домен. Список endpoint
поможет только пока в нём остаётся доступный сервер. ТСПУ также может смотреть
на SNI, сертификат, TLS ClientHello, длительность соединения и интервалы между
пакетами.

Go-клиент копирует структуру ClientHello, но не становится настоящим Chrome или
Firefox. Версии браузеров меняются, а профиль uTLS может устареть. Так что нужны
обновления и проверка на реальных сетях разных операторов.

Сообщение `possible ClientHello filtering` означает только место сбоя. Оно не
доказывает, что соединение заблокировал именно РКН: похожую ошибку может дать
нестабильная сеть или несовместимый TLS-сервер.

То же относится к переключению endpoint. Клиент видит этап ошибки, но не может
точно узнать её причину или отличить блокировку от обычного сбоя сети.

Подробная модель угроз лежит в [`docs/THREAT_MODEL.md`](docs/THREAT_MODEL.md).
